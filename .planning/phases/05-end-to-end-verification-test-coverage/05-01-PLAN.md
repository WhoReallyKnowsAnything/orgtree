<objective>
Prove VER-01: a packaged, launched macOS build of Orgtree can spawn one real coding-agent CLI turn and show the result back in the app, with no manual workaround beyond the already-documented Gatekeeper approval step (PKG-03).

Purpose: `tests/acceptance/run.mjs` is the project's only existing full-Electron acceptance harness, but its own `limits` array states `'No real provider turn in this suite'` [VERIFIED: tests/acceptance/run.mjs:116] — it proves the app launches and restarts cleanly, never that an agent does real work. Separately, `tests/acceptance/run_claude.py` and `tests/acceptance/run_provider.py` already exist as real, human-gated single-turn provider tests (Claude subscription lane and Codex "Luna" lane respectively) — but both bypass Electron entirely, spawning `engine.launch.load_app()` directly in a bare Python process [VERIFIED: tests/acceptance/claude_engine.py:12-31]. Neither artifact alone proves the full "package → launch → real agent job → visible result" chain the roadmap requires. This plan builds that chain by porting `run_claude.py`'s proven hire/message/observe assertions into the Electron-launched, DOM-driven harness shape of `tests/acceptance/application.cjs`, and adds a static pre-flight gate for two source-verified process-lifecycle gaps that would otherwise make the resulting run silently flaky.

Output: `tests/acceptance/run_agent_turn.mjs` + `agent_turn.cjs` (a new VER-01 acceptance runner), `tools/verify-macos-preflight.mjs` (a pre-flight dependency gate), and a filled-in hardware verification record.

**Cross-phase dependency (read before executing):** Phases 1-4 of this roadmap have not been executed yet (`.planning/STATE.md`: `completed_phases: 0`). Task 1 and Task 3 below cannot reach a real PASS until Phase 1 ships a `mac` electron-builder target (PKG-01) and Phase 2 lands the provider process-tree fix this plan's Task 2 checks for. Task 2 is fully executable today, on any POSIX machine, against the current (unfixed) source — it is not blocked. Each task states its blocked-vs-now status explicitly.

**Resolved open question (RESEARCH.md A3):** RESEARCH.md flagged that `mcp__macos-harness` (`build_app`/`launch_app`/`ax_tree`) was not available as a callable tool during research and recommended the executor check its own tool list at execution time, falling back to the `spawnSync`+structured-report pattern already proven in `run.mjs` if absent. This plan does not depend on `mcp__macos-harness` at all — Task 1 uses `run.mjs`'s existing `spawnSync(electron, ...)` launch pattern exclusively, so the open question does not block this plan regardless of which way it resolves on the execution host.

**A newly-discovered gap beyond RESEARCH.md's Pitfall 3:** `engine/process_lifetime.py::arm_process_lifetime` — called unconditionally from `engine/launch.py:358-361` on every engine start, not just the boot-host path — raises `RuntimeError("process ownership is currently supported on Windows only...")` whenever `os.name != "nt"` [VERIFIED: engine/process_lifetime.py:28-29]. Unlike the codexrun.py/antigravityrun.py provider-kill gap (attributed to PROC-03/Phase 2 by RESEARCH.md), this guardian is explicitly out-of-scope for any provider ("It never imports the API, reads credentials, or dispatches a provider" [VERIFIED: engine/process_lifetime.py:5]) and is not literally named by PROC-01/02/03's wording — meaning the Python engine cannot start AT ALL on macOS today, and no Phase 1-4 requirement as currently worded explicitly claims the fix. Task 2's pre-flight gate treats this as a named, blocking dependency rather than silently assuming it will be fixed. If Phase 2 planning does not already cover it, flag this to the user before Phase 2 executes.
