## Summary

The Windows guardian's guarantee rests on one Windows-only property: **Job Object membership is transitive and automatic** — every process spawned by any Job member joins the Job unless it explicitly opts out, so `TerminateJobObject` reliably kills the *entire* tree in one call, and `WaitForMultipleObjects` blocks on arbitrary handles (child or not) until any one signals. POSIX has no single primitive with both properties. The adapter needs two independent mechanisms glued together: (1) **`select.kqueue()` with `EVFILT_PROC`/`NOTE_EXIT`** (verified live in this session: `select.KQ_FILTER_PROC`, `select.KQ_NOTE_EXIT`, `select.KQ_EV_ADD`, `select.KQ_EV_ONESHOT` all present in stdlib on this Darwin arm64 machine, Python 3.10.13) to detect exit of *arbitrary* PIDs — this is required because `os.waitpid()` only works on the caller's own children, and **the guardian is not the engine's parent — the engine is the guardian's parent** (the engine calls `subprocess.Popen` to spawn the guardian), so `os.waitpid(engine_pid, ...)` would fail with `ECHILD`; and (2) an explicit **recursive PID enumeration** (via `ps -axo pid=,ppid=`, verified working on this machine) to build the guardian's own descendant map at teardown time, because a single `os.killpg()` on the engine's process group will **not** reach any provider CLI process that the existing (Phase 2) code spawns with `start_new_session=True` — those processes deliberately escape into their own session for *individual* per-agent-stop isolation, which is a different, already-decided mechanism this phase must not break.

A third concrete, verified gap: `engine.ts:195` spawns the Python engine via Node's `spawn()` **without** `detached: true`, so on macOS the engine currently inherits the **same process group as the Electron main process**. Neither the guardian nor any `killpg` call can safely target that group as-is (it would also kill the desktop shell). The engine itself must call `os.setpgid(0, 0)` early in its own startup (self-directed process-group calls are always permitted; parent/unrelated-process calls are not) to become its own group leader before any provider is spawned.

The env-var allowlist in `arm_process_lifetime()` (`allowed = {"SYSTEMROOT", "WINDIR", "TEMP", "TMP", "PATH", "SYSTEMDRIVE", "COMSPEC"}`) is Windows-specific and needs a POSIX branch (no `HOME`/`TMPDIR`/`USER` today).

**Primary recommendation:** Add a `PosixTree` class next to `WindowsTree` with the same public surface (`arm()`, `wait()`, `terminate(code, stalled=None)`, `close()`), dispatched from `watch()` exactly like `RootLock` already dispatches on `os.name`. `PosixTree.wait()` uses one `kqueue` watching both `engine_pid` and `parent_pid` via `EVFILT_PROC`/`NOTE_EXIT`. `PosixTree.terminate()` repeatedly (1) enumerates all live descendants of `engine_pid` by shelling out to `ps -axo pid=,ppid=` and walking the ppid chain, (2) `os.killpg()`s every distinct process-group id found among them (catching whole provider-CLI sessions in one shot each) and individually `os.kill(pid, SIGKILL)`s any straggler not swept by step 2, and (3) re-enumerates until empty or a stall deadline, mirroring `WindowsTree.terminate()`'s `QueryInformationJobObject` polling loop and its `stalled()` diagnostic callback. No new third-party dependency (no `psutil`) — this matches Phase 2's own decision to reject `psutil` in favor of stdlib `os.killpg` (`02-RESEARCH.md:158`).

### Pattern 1: Dual-PID exit detection with a single kqueue

**What:** One `select.kqueue()` instance registers `EVFILT_PROC`/`NOTE_EXIT` kevents for both `engine_pid` and `parent_pid`; a single blocking `control(None, 1)` call returns as soon as either process exits — this is the direct POSIX analogue of `WaitForMultipleObjects(..., bWaitAll=False, ...)` over the two Windows handles in `WindowsTree.wait()` (`process_lifetime.py:202-207`).
**When to use:** `PosixTree.wait()`, replacing `WindowsTree.wait()`'s Windows-only body.
**Example:**
```python
# Source: docs.python.org/3/library/select.html#kqueue-objects (API) +
# gmpy.dev/blog/2026/event-driven-process-waiting (pattern) — verified live this session:
# select.KQ_FILTER_PROC / select.KQ_NOTE_EXIT / select.KQ_EV_ADD / select.KQ_EV_ONESHOT
# all present in stdlib `select` on Darwin arm64, Python 3.10.13.
import select

def wait_for_either_exit(engine_pid: int, parent_pid: int | None) -> None:
    kq = select.kqueue()
    try:
        idents = [engine_pid] + ([parent_pid] if parent_pid else [])
        events = [
            select.kevent(pid, filter=select.KQ_FILTER_PROC,
                           flags=select.KQ_EV_ADD | select.KQ_EV_ONESHOT,
                           fflags=select.KQ_NOTE_EXIT)
            for pid in idents
        ]
        kq.control(events, 0, 0)          # register; no wait
        kq.control(None, 1)               # block until first NOTE_EXIT fires
    finally:
        kq.close()
```
Registering an already-exited PID reports the pending event immediately rather than blocking forever or raising — [CITED: jmmv.dev/2019/11/wait-for-process-group-darwin.html — "registering for an event reports any pending such events, so this is not racy if the process happened to exit before installation"]. This closes the most dangerous race (target already dead at registration time); a much smaller residual PID-reuse risk remains for the duration of the `wait()` call itself — see Pitfall 3.

### Pattern 2: Full descendant enumeration and sweep (no `/proc`, no `psutil`)

**What:** Build the descendant set of `engine_pid` by parsing `ps -axo pid=,ppid=` output (macOS has no procfs), then kill by distinct process-group id first (cheap, catches whole provider sessions in one call each), then sweep any individually-remaining PID.
**When to use:** `PosixTree.terminate()`, replacing `WindowsTree.terminate()`'s `QueryInformationJobObject` polling loop.
**Example:**
```python
# Source: verified live this session — `ps -axo pid,ppid,pgid,comm` on Darwin 27.2.0 arm64
# returns whitespace-columnar pid/ppid/pgid/comm; `ps -axo pid=,ppid=` (no header, `=` suppresses
# the column title) is the standard BSD-ps idiom for script-parseable output.
import os
import signal
import subprocess

def live_descendants(root_pid: int) -> set[int]:
    out = subprocess.run(["ps", "-axo", "pid=,ppid="], capture_output=True, text=True, check=True).stdout
    by_parent: dict[int, list[int]] = {}
    for line in out.splitlines():
        parts = line.split()
        if len(parts) != 2:
            continue
        pid, ppid = int(parts[0]), int(parts[1])
        by_parent.setdefault(ppid, []).append(pid)
    found: set[int] = set()
    frontier = [root_pid]
    while frontier:
        parent = frontier.pop()
        for child in by_parent.get(parent, []):
            if child not in found:
                found.add(child)
                frontier.append(child)
    return found

def sweep(root_pid: int) -> None:
    descendants = live_descendants(root_pid) | {root_pid}
    pgids: set[int] = set()
    for pid in descendants:
        try:
            pgids.add(os.getpgid(pid))
        except ProcessLookupError:
            continue
    for pgid in pgids:
        try:
            os.killpg(pgid, signal.SIGKILL)
        except ProcessLookupError:
            pass
    for pid in descendants:
        try:
            os.kill(pid, signal.SIGKILL)
        except ProcessLookupError:
            pass
```
The `killpg`-then-individual-`kill` combination deliberately does not assume every descendant shares one process group: `gitrunner.py`'s existing pattern (`02-RESEARCH.md:147-148`; `gitrunner.py:72` — `start_new_session=os.name != "nt"`) intentionally puts each spawned provider CLI into its **own** session, so a naive single `os.killpg(engine_pgid, ...)` would never reach them — see Pitfall 1.

### Anti-Patterns to Avoid

- **A single top-level `os.killpg(engine_pgid, SIGKILL)` as the whole teardown mechanism:** Looks like the natural POSIX equivalent of `TerminateJobObject`, but Phase 2 already put every provider CLI spawn into its own session (`start_new_session=True`) for per-agent-stop isolation. A single group kill on the engine's own group will silently leave every running provider process alive. Use the enumerate-and-sweep pattern (Pattern 2) instead, which is agnostic to how many distinct groups exist under the engine.
- **`os.waitpid(engine_pid, ...)` from inside the guardian:** The guardian is spawned BY the engine (`subprocess.Popen` in `arm_process_lifetime`), so the engine is the guardian's OS parent, not its child — `waitpid` can only wait on your own children and will raise `ECHILD`. Use `kqueue`/`EVFILT_PROC` instead (Pattern 1), which has no parent/child requirement.
- **Reusing the Windows-only env allowlist unmodified:** `allowed = {"SYSTEMROOT", "WINDIR", "TEMP", "TMP", "PATH", "SYSTEMDRIVE", "COMSPEC"}` (`process_lifetime.py:41`) carries zero POSIX-specific entries (`HOME`, `TMPDIR`). `PATH` is shared so the guardian will still start, but this should be branched on `os.name` like the `RootLock` locking call already is, not left as dead Windows-only surface silently shipped into the POSIX guardian's environment.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Detecting exit of a PID you don't own (not your child) | A homegrown polling loop with exponential backoff around `os.kill(pid, 0)` | `select.kqueue()` + `EVFILT_PROC`/`NOTE_EXIT` | Kernel-native, zero busy-polling, closes the registration-time race for free — [CITED: gmpy.dev/blog/2026/event-driven-process-waiting] |
| Full descendant discovery on macOS | A recursive shell pipeline or a new `psutil` dependency | `ps -axo pid=,ppid=` parsed once per `terminate()` iteration into a ppid→children map | No procfs on Darwin, so `psutil` is the only third-party shortcut — and Phase 2 already rejected it (`02-RESEARCH.md:158`) for the equivalent problem; the `ps` parse is ~15 lines of stdlib code |

**Key insight:** the Windows guardian gets two capabilities "for free" from a single OS primitive (Job Objects): transitive process-tree membership AND arbitrary-handle waiting. POSIX has neither for free — this phase is fundamentally about composing two separate, narrower primitives (`kqueue` for waiting, `ps`-based enumeration for tree membership) to reconstruct the same guarantee, not finding one drop-in replacement.

## Common Pitfalls

### Pitfall 1: The engine's process group is currently shared with the Electron desktop shell
**What goes wrong:** Any `os.killpg()` targeting the engine's process group before the group is changed would also kill the Electron main process (the desktop shell itself), since `child_process.spawn()` in `engine.ts` does not set `detached: true` — [VERIFIED: `apps/desktop/main/engine.ts:195` reads `spawn(options.python, [...], { cwd: options.directory, env, windowsHide: true, stdio: 'pipe' })` — no `detached` key present].
**Why it happens:** POSIX child processes inherit their parent's process group by default unless the spawning call explicitly detaches them, or the child calls `setpgid` on itself.
**How to avoid:** Have the Python engine call `os.setpgid(0, 0)` on itself as early as possible in `launch.py::main()` — ideally before `arm_process_lifetime()` is called, and definitely before any provider subprocess is spawned, so every later spawn inherits the correct (new, engine-owned) group by default. `os.setpgid(0, 0)` on oneself is always permitted regardless of parent relationship — [CITED: docs.python.org/3/library/os.html#os.setpgid — POSIX permits a process to set its own group id]. Do not attempt this from inside the guardian (`PosixTree`) — the guardian is not the engine's parent and `setpgid` on an unrelated process raises `EPERM`.
**Warning signs:** A teardown test that kills the Electron parent process in a test harness would surface this immediately (the "positive control" pattern already used in `test_process_lifetime.py::alive()` should be extended to also assert the *parent* stays alive when only the engine's tree is torn down — no such assertion exists in the current Windows-only suite, since Windows Job Objects never had this failure mode).

### Pitfall 2: Provider CLI processes each have their own process group by design — a single `killpg` will not reach them
**What goes wrong:** Because Phase 2 (`gitrunner.py:72`, and its planned extension to `codexrun.py`/`antigravityrun.py` per PROC-03) spawns every provider CLI with `start_new_session=True`, each provider process is the leader of its own new session/group — not a member of the engine's group. `os.killpg(engine_pgid, ...)` alone leaves them all running.
**Why it happens:** `start_new_session=True` was chosen deliberately (in Phase 2) so a single agent could be stopped via `os.killpg(proc.pid, SIGKILL)` without taking down the whole engine or other agents' processes. That per-agent isolation and this phase's full-tree teardown are solving different problems with the same primitive, and naively reusing the primitive at the wrong scope breaks the other one.
**How to avoid:** Use Pattern 2 (enumerate-then-sweep) — it finds every live descendant regardless of which group each belongs to, and kills by distinct `pgid` (efficient) plus individual pid (correctness backstop), rather than assuming one shared group covers everyone.
**Warning signs:** A teardown test that spawns a fake "provider" child with `start_new_session=True` under the fake engine and checks it dies when the fake engine's parent-death path fires — this is exactly the shape of `test_process_lifetime.py::test_desktop_parent_exit_kills_owned_tree`, but that test's fake engine's own worker script (`process_lifetime.py`'s in-test `worker.py` fixture, lines 66-68) spawns its child with plain `subprocess.Popen` (no `start_new_session`), so it does NOT currently exercise this gap — a new test case is needed that spawns a grandchild with `start_new_session=True` to prove the sweep still reaches it.

### Pitfall 3: PID reuse is a residual (not eliminated) risk for long-running watches
**What goes wrong:** `kqueue`'s `EVFILT_PROC` registration is race-free at registration time (an already-exited PID reports immediately), but the watch is still keyed on a bare integer PID for its entire lifetime. If the watched process exits and, in a vanishingly unlikely but non-zero window, the OS reuses that exact PID for a new unrelated process before `NOTE_EXIT` fires for the original... (in practice this cannot happen: the kernel delivers the pending `NOTE_EXIT` for the *original* process at or before PID reuse is possible, since the PID is held by the kernel as a zombie/reserved until reaped or otherwise released — this is the same guarantee that makes `waitpid` itself race-free). The more realistic residual risk is at the boundary: the guardian receives `engine_pid`/`parent_pid` as plain integers over the handshake/CLI args (`process_lifetime.py:44`, `--watch <root> <engine_pid> <parent_pid>`), and if the true engine process had already died and its PID been reused by the time the guardian registers its kqueue watch, the guardian would silently watch the wrong process.
**Why it happens:** Fundamental to any PID-based API on POSIX (this equally affects `os.kill(pid, 0)` polling, which is *more* exposed since it re-checks on every tick rather than once).
**How to avoid:** This is not new: the existing Windows path has an equivalent (if narrower) exposure via `OpenProcess(..., engine_pid)` at `WindowsTree.__init__` racing against process death, and the existing handshake protocol already keeps the window as tight as possible (the guardian receives and opens/registers against the engine PID within the same synchronous startup sequence that spawned it, milliseconds after the engine's own `os.getpid()` call at `process_lifetime.py:44`). No code change beyond faithfully preserving this tight-window property is warranted; flag as a documented, accepted risk rather than something this phase needs to newly solve.
**Warning signs:** None specific to this phase — this is a pre-existing, platform-agnostic property of PID-based process tracking, not a regression introduced by the POSIX adapter.

### Pitfall 4: The Windows-only env allowlist silently ships into the POSIX guardian's environment
**What goes wrong:** `env = {k: v for k, v in os.environ.items() if k.upper() in allowed}` (`process_lifetime.py:41-42`) uses `allowed = {"SYSTEMROOT", "WINDIR", "TEMP", "TMP", "PATH", "SYSTEMDRIVE", "COMSPEC"}`. On POSIX this silently drops `HOME`, `TMPDIR`, `USER`, `LANG` — everything except `PATH` and (if literally set) `TEMP`/`TMP`.
**Why it happens:** The allowlist was written when only Windows was supported and was never revisited.
**How to avoid:** Branch the allowlist on `os.name`, matching the `RootLock`/`creationflags` pattern already used elsewhere in the same function. The guardian's own contract ("never imports the API, reads credentials, or dispatches a provider" — `process_lifetime.py` module docstring) means it likely does not *need* `HOME`, but a bare `PATH`-only environment is a real deviation from "isolated but sane" and should be an explicit, reviewed choice, not an accidental byproduct of copy-pasting a Windows list.
**Warning signs:** Any future guardian code path that touches `tempfile`, `Path.home()`, or subprocess resolution via `shutil.which()` would behave differently (or fail) under this reduced environment versus a developer's normal shell.

## Open Questions

1. **Should the process-group fix (Pitfall 1) live in `launch.py` (Python, self-`setpgid`) or `engine.ts` (Electron, `detached: true`)?**
   - What we know: Both close the gap. `engine.ts:195` is verified to currently lack `detached: true`. Self-`setpgid(0,0)` is verified-permitted POSIX behavior requiring no permission the engine doesn't already have.
   - What's unclear: Whether the project wants this phase (scoped to "engine process lifetime POSIX adapter," i.e. Python-side) to also touch the Electron spawn call, or whether that's intentionally deferred/out of scope and the Python-side self-`setpgid` is the sole intended fix.
   - Recommendation: Default to the self-`setpgid` fix in `launch.py` only (keeps the change inside `engine/`, matches the phase's stated scope and depends-on chain), and flag the `engine.ts:195` finding to the planner as a documented, not-fixed-here observation, unless the plan explicitly decides to touch both files.

2. **Does `tree.arm()` need any real POSIX body, or is it a no-op?**
   - What we know: On Windows, `arm()` performs the actual `AssignProcessToJobObject` call — this is the moment ownership legally begins, separate from `__init__`'s handle-opening. On POSIX, the design in this document has the guardian's "ownership" consist entirely of (a) holding the two `kqueue` watches and (b) knowing `engine_pid` for later enumeration — both of which are already fully set up by `PosixTree.__init__`.
   - What's unclear: Whether `watch()`'s existing handshake structure (prepare → `arm` → ready) still needs a distinct `PosixTree.arm()` call with real effect, or whether it becomes a no-op kept only to preserve the shared `watch()` code path and the two-phase handshake's cancel-ability guarantee (a slow/failed prepare can still be cancelled by the caller before `arm` is sent, exactly as today).
   - Recommendation: Keep `arm()` as a no-op (`self.armed = True`) on `PosixTree` — the cancel-before-arm guarantee is about the *caller's* behavior (not sending `"arm\n"` on timeout), not about anything the tree object itself needs to gate. This preserves the existing `watch()` function nearly verbatim, which best matches the phase's "smallest change" framing.
