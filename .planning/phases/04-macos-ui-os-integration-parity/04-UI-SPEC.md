# Phase 4 — UI Design Contract

> Visual and interaction contract for Phase 4 (macOS UI & OS Integration Parity). Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

This phase is **Electron main-process / OS-chrome work**, not a new screen. Nothing in scope adds
a renderer page, list, or form. Four of the five UI requirements (UI-01, UI-02, UI-03, UI-05) never
touch the renderer at all — they are Dock/menu-bar/tray API calls against the OS. Only UI-04
(badge count, computed from existing data) and UPD-01 (one new copy variant on the existing
`UpdateNotice` component) touch anything a user reads on screen. Accordingly:

- **Design System / Spacing / Typography / Color** below are declared for completeness (checker
  Dimensions 3–5) but marked **not exercised** — this phase introduces no new visual language and
  must not invent one. The one new renderer string (UPD-01's mac copy) inherits the existing
  `.update-notice` container and CSS already shipping in `apps/desktop/renderer/src/styles.css`.
- The load-bearing content of this contract is the **OS Integration Contract** and **Copywriting
  Contract** sections — menu structure, Dock/badge/bounce behavior, and exact update-notice copy.

## OS Integration Contract

> This is the actual design contract for Phase 4. Each subsection maps 1:1 to a v1 requirement.

### App Menu (UI-03)

No `Menu.setApplicationMenu` call exists anywhere in `apps/desktop/main` today. Add exactly this
template — no more, no less (no File menu, no Help menu: nothing in scope needs either, and
`Edit`/`Window` are required for standard mac keyboard behavior to work at all, not decoration):

| Menu | Items (in order) | Notes |
|------|-------------------|-------|
| **Orgtree** (`role: 'appMenu'`) | About Orgtree (`role: 'about'`) · separator · Preferences… (`Cmd+,`) · separator · Services (`role: 'services'`) · separator · Hide Orgtree (`role: 'hide'`) · Hide Others (`role: 'hideOthers'`) · Show All (`role: 'unhide'`) · separator · Check for Updates… · separator · Quit Orgtree (`role: 'quit'`) | Electron auto-fills the menu's own label from `app.name` when `role: 'appMenu'` is used — do not hardcode "Orgtree" as the role-menu label. |
| **Edit** (`role: 'editMenu'`) | Undo, Redo, Cut, Copy, Paste, Select All (+ native Speech submenu) | Use the built-in role wholesale — this is what makes `Cmd+C`/`Cmd+V`/`Cmd+Z` work in any text field at all; do not hand-roll individual items. |
| **Window** (`role: 'windowMenu'`) | Minimize, Zoom, separator, Bring All to Front | Use the built-in role — it also auto-populates the open-window list, which this app needs nothing custom for. |

- **Preferences… (`Cmd+,`)**: click handler sends an IPC message to the focused window that opens
  the existing `SettingsPanel` (already present in `App.tsx`) — do not build a second settings
  surface.
- **Check for Updates…**: click handler calls the *same* `checkForUpdates()` function the tray's
  existing "Check for updates" row already calls — one implementation, two entry points. Its
  resulting label follows the Copywriting Contract below (including the new mac-only
  `update-available` copy).
- **Quit Orgtree**: no confirmation dialog. The Python engine and any in-flight agent jobs run as a
  separate background process (per Phase 3's `launchd` LaunchAgent) independent of the Electron UI
  process, so quitting this menu item never loses running work — document this explicitly so the
  executor doesn't add an unrequested "are you sure?" prompt.

### Window Lifecycle (UI-02)

`app.on('activate', show)` and `app.on('window-all-closed', ...)` already exist and are already
correct in shape (no quit-on-last-window-close). The one real gap: `show()` (`apps/desktop/main/
index.ts` ~L221) only shows/restores an existing `main` window — it does nothing if `main` has been
fully destroyed.

- **Contract**: `show()` must check `!main || main.isDestroyed()` and, if true, recreate the main
  window using the exact same window-creation path already used at app startup (same
  `configureWindow` call, same persisted-layout restore) — not a second, divergent construction
  path.
- Clicking the Dock icon with zero windows open must always result in exactly one window opening
  (never zero, never two).

### Dock Attention / Bounce (UI-01)

Replaces `TaskbarAttention`'s `flashFrame` call on macOS with `app.dock.bounce('critical')` —
same triggering semantics as the existing class already implements, just a different platform call:

- **Trigger**: identical "arrival" logic already in `TaskbarAttention.set(ids)` — a genuinely NEW
  id entering the qualifying set (pending asks / urgent mail) starts a bounce; the same ids seen
  again on a later poll do not re-bounce; one id resolving while others remain waiting does not
  stop or restart anything.
  the qualifying set draining to empty stops it.
- **Bounce type**: `'critical'` (bounces continuously until canceled), matching success criterion
  #1 literally — not `'informational'` (single bounce).
  - **Cancel**: call `app.dock.cancelBounce(id)` (the id `bounce()` returns) when the main window
    receives `focus`, mirroring the existing `taskbarAttention.focused()` call site exactly — same
    event, same place, different platform API underneath.
- This is the same class (`TaskbarAttention` or its mac-aware successor), not a parallel
  implementation — the identity-set logic must not be duplicated per platform.

### Dock Badge (UI-04)

- **Source of truth**: the exact same qualifying identity set that drives the Dock bounce above
  (pending asks + unread urgent mail across all orgs) — one shared count, not a second counter that
  could drift from it.
- `app.setBadgeCount(ids.length)` fires at the same call site as the bounce-arrival check, every
  time the set changes (not just on arrival — the badge is a standing count, the bounce is a
  one-shot event).
- `ids.length === 0` → `app.setBadgeCount(0)`, which clears the badge (Electron/macOS default).
- No custom formatting: pass the raw integer. macOS renders it as-is; no "99+" truncation logic is
  needed or wanted — every native mac app leaves this to the OS.

### Tray Template Icon (UI-05)

- **Base glyph**: a single monochrome (black-on-transparent) "Orgtree eye" silhouette image, loaded
  via `nativeImage` with `.setTemplateImage(true)` set before assigning it to the `Tray`. macOS then
  handles light/dark menu-bar inversion automatically — this satisfies the requirement literally
  and needs no manual light/dark branching in app code.
- **Tooltip**: keep the existing `tray.setToolTip(\`Orgtree - ${label()}\`)` call unchanged — it
  already carries the provider/engine-state text that the icon itself can no longer show in color
  (see the flagged tradeoff below).
- ⚠ **Provider color-coding tradeoff** (flagged, not silently decided — see UI Considerations):
  the current tray already recolors the eye per active provider theme
  (`orgtree-eye-tray-{claude,codex,antigravity,openrouter,orgtree,grey}.ico`) via pixel
  recoloring in `runtimeIcon()`. A macOS **Template** image is alpha-channel-only — the OS discards
  color information and renders it black/white regardless of the source pixels — so that
  recoloring becomes invisible in the menu bar the moment Template mode is on. The default
  resolution below is a documented assumption, not a locked product decision:
  - Default: ship the single monochrome Template glyph, keep the tooltip/menu label as the carrier
    of provider/engine-state information (no visual information is silently dropped — only the
    color cue), and do not build a second image.
  - If the color signal must survive in the menu bar itself, the follow-up option is
    `tray.setTitle(text)` (macOS-only), which renders text beside the icon in the system's own
    label color — already theme-correct for free, no new palette needed. Not built by default;
    flagged for planner/executor confirmation before deciding.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (mac update notice) | "View release" — opens the release page in the default browser via `shell.openExternal`, reusing the URL the existing update-check feed already resolves. Never "Update now" / "Install" on macOS — UPD-01 forbids offering an auto-apply action here. |
| App menu — Preferences | "Preferences…" (`Cmd+,`) |
| App menu — Check for Updates | "Check for Updates…" |
| App menu — Quit | "Quit Orgtree" (`role: 'quit'`, no custom label needed) |
| Mac update-available label | `Orgtree {version} is available` — same version-naming convention `updateActionTitle()` already uses (the downloaded/available release, never the running one) |
| Mac tray update row (replaces "Update now"/"Automatic updates" on mac) | `Orgtree {version} available — View release` (single row, click opens the release page) |
| Update check unreachable (existing, unchanged) | "Update check unavailable" — reused verbatim from `LABEL.unavailable`, applies identically on mac |
| Empty state | Not applicable — this phase adds no list/collection UI |
| Error state — release page fails to open | "Couldn't open the release page — copy the link from Check for Updates and open it manually." (only shown if `shell.openExternal` rejects) |
| Destructive confirmation — Quit | None required. The engine/agent jobs run in a separate background process (Phase 3 `launchd` LaunchAgent); quitting the Electron app does not stop in-flight work, so no confirmation dialog is added. |

## UI Considerations

Applicable state considerations resolved: 6 covered, 2 backstop, 1 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| zero-one-many | Dock bounce + badge count | ✅ covered | Same `ids.length`/arrival semantics as the existing `TaskbarAttention`: 0 clears bounce+badge, re-seen ids never re-bounce, one id resolving doesn't disturb the rest. |
| empty | Dock icon clicked with zero windows open | ✅ covered | `activate`/`show()` recreates a destroyed main window via the same startup construction path — never leaves the Dock icon inert. |
| populated | Tray icon in light vs dark menu bar | ✅ covered | `setTemplateImage(true)` — OS-native auto-inversion, no app-side branching. |
| overflow | Provider color signal vs. monochrome Template constraint | ⚠ unresolved | Template images cannot carry color; default keeps the signal in tooltip/menu text only. Needs planner/product confirmation before implementation — see OS Integration Contract → Tray Template Icon. |
| long-text | Version string interpolated into update-notice copy | 🧪 backstop | Relies on the existing `.update-notice` container rule already in `styles.css` (`max-width: min(280px, 34vw); overflow-wrap: anywhere`) — no new wrapping rule added; verify at implementation time with an unusually long version/build string. |
| error | Update feed unreachable during a mac check | ✅ covered | Reuses the existing `unavailable` → "Update check unavailable" label unchanged. |
| zero-one-many | Very large pending badge count (e.g. hundreds of unread items) | ✅ covered | No truncation/formatting — `app.setBadgeCount()` passed the raw integer, matching native mac app conventions. |
| partial | Edit-menu item enabled/disabled state with no field focused | 🧪 backstop | `role: 'editMenu'` self-manages enable/disable via native focus tracking; no custom code — verify by hand once wired up (no automated test surface for OS menu enablement). |
| populated | App menu "Check for Updates…" reaching the new mac `update-available` state | ✅ covered | Same `checkForUpdates()` implementation as the tray row — one code path, two entry points, so the two surfaces cannot drift in wording (mirrors the existing `describeUpdateStatus` sharing pattern in `update-notice.tsx`). |
