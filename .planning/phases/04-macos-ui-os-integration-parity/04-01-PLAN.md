<objective>
Wire the one requirement in this phase that crosses every layer (contracts → preload → main → renderer, plus the tray as a second entry point) end-to-end first: the macOS "new version available" notice, which never offers an auto-apply install. Then expand outward to the Dock's two native attention signals — bounce and badge — which already share one identity-set implementation in this codebase and must keep sharing it.

Purpose: Orgtree currently has no way to tell the renderer (or the tray) it is running on macOS, and no way to open a URL from the renderer without a new IPC surface. Establishing that bridge/IPC pattern here, on the most visible user-facing requirement, de-risks it before the remaining OS-chrome work (Plan 04-02) builds on the same conventions.
Output: A working, tested macOS update notice (in-app and tray) that never offers auto-install, plus a native Dock bounce + badge that share one identity set with the existing taskbar-attention logic.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → main (IPC) | The untrusted renderer process invokes `desktop:open-release-page` and `desktop:pending-attention` across the `contextBridge`/`ipcRenderer.invoke` boundary. |
| main → OS (Dock/Tray/shell APIs) | The trusted Electron main process calls `app.dock.bounce`, `app.setBadgeCount`, and `shell.openExternal` — no external/untrusted input reaches these calls in this plan. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `desktop:open-release-page` IPC handler (index.ts) | medium | mitigate | Handler accepts zero renderer-supplied arguments and only ever calls `shell.openExternal(MANUAL_UPGRADE_URL)` — the existing hardcoded constant — never a renderer-controlled URL, closing off the classic Electron arbitrary-external-URL-open vulnerability class. |
| T-04-02 | Denial of Service | Rapid `desktop:pending-attention` calls spamming the Dock bounce | low | accept | Existing arrival-only semantics in `TaskbarAttention.set()` (unchanged by this plan) already suppress re-triggering on repeated polls of the same id set. |
| T-04-03 | Spoofing | A compromised renderer forging `desktop:pending-attention` payloads with attacker-chosen ids | low | accept | Ids are opaque strings already normalized by the existing `attentionIdentities()` (unchanged); a forged id only affects the local bounce/badge count display, no privilege or data-access change results. |

</threat_model>
