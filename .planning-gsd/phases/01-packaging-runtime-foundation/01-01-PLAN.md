</objective>

  <name>Task 1: Provision a macOS Python runtime via python-build-standalone (RUN-01)</name>
  <files>tools/provision-runtime.py</files>
  <action>Add a macOS branch to provision-runtime.py, parallel to the existing win32 branch (do not touch the win32 `main()` body). Guard it with `sys.platform == "darwin"` (raise SystemExit for any other non-win32 platform, mirroring the existing "requires a Windows build host" refusal style). Resolve the target arch from an `ORGTREE_RUNTIME_ARCH` environment variable (accepting `aarch64`/`x86_64`, astral-sh's own naming), defaulting to the host's native arch via `platform.machine()` (map `arm64` to `aarch64`). Download `cpython-3.13.15+20260901-ARCH-apple-darwin-install_only.tar.gz` (ARCH being `aarch64` or `x86_64`) from the `astral-sh/python-build-standalone` GitHub release tag `20260901` (same VERSION constant already pinned, `3.13.15`) into `.runtime-cache/`, mirroring the existing win32 branch's cache-then-verify-then-extract structure. Verify the downloaded tarball's SHA256 against astral-sh's published per-release checksum for that exact asset before extracting — do not hardcode an unverified hash; fetch or pin one only after confirming it against the release page, matching the existing `hashlib.sha256(...) != SHA256: raise SystemExit` pattern already used for the Windows zip. Extract into `engine/runtime/` (same `RUNTIME` constant, same symlink-refusal check already used for win32). Do not create per-arch subdirectories — `engine/runtime/` holds exactly one provisioned arch at a time, the same invariant as the Windows branch; provisioning a second arch means re-running with a different `ORGTREE_RUNTIME_ARCH` after the first is staged or packaged. After extraction, pip-install `tools/runtime-requirements.in` into `engine/runtime/lib/python3.13/site-packages` using the build host's own `sys.executable -m pip install --disable-pip-version-check --only-binary=:all: --target ENGINE_RUNTIME_SITE_PACKAGES_DIR --upgrade --no-warn-conflicts --report REPORT_JSON_PATH`, with `--platform`/`--python-version 3.13`/`--implementation cp`/`--abi cp313` tags matching the target arch (for example `macosx_11_0_arm64` for aarch64, `macosx_11_0_x86_64` for x86_64 — confirm the exact minimum-OS tag against the packages' actually published wheels on PyPI before relying on it, since a wrong tag fails pip resolution closed rather than silently). Write `engine/runtime/runtime-manifest.json` from the pip `--report` output, the same shape as the Windows branch (`python`, `url`, `sha256`, `dependencies: [{name, version, download}]`). Because python-build-standalone's layout has no `._pth` file (unlike the Windows embeddable zip) and a `._pth` interpreter's PYTHONPATH-ignoring behavior has no macOS equivalent, write a plain `.pth` file (for example `orgtree.pth` — a normal CPython `site`-processed path file, not `._pth`) into `engine/runtime/lib/python3.13/site-packages/` containing relative-path entries that resolve, from that site-packages directory, to the same three locations the Windows `_pth`'s `../backend`, `../mailhub`, and `../../` entries reach relative to `engine/runtime` — namely `engine/backend`, `engine/mailhub`, and the repository root. Since site-packages sits three directories below `engine/runtime` on this layout (`lib/python3.13/site-packages`), each relative entry needs three extra `../` segments compared with the Windows entries. Finish with a smoke-import subprocess call using `engine/runtime/bin/python3.13` (not `python.exe`) that imports `sys, sqlite3, ssl, fastapi, uvicorn, websockets, httpx, PIL, psutil`, asserts `importlib.util.find_spec('engine')` and `importlib.util.find_spec('mailhub')` both resolve, and prints `sys.version`/`sys.executable` — mirroring the Windows branch's smoke test exactly, adapted for the macOS interpreter path.</action>

  </verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build host -> astral-sh GitHub releases (network) | provision-runtime.py downloads an executable Python interpreter + stdlib archive over HTTPS from a third-party release host |
| Downloaded tarball -> local filesystem (extraction) | tar extraction can be exploited via crafted archive entries (path traversal, symlink escape) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | tools/provision-runtime.py (macOS tarball download) | high | mitigate | Verify SHA256 against astral-sh's published per-asset checksum before extraction, mirroring the existing hashlib.sha256 check already gating the Windows zip; refuse extraction on mismatch |
| T-01-02 | Tampering | tools/provision-runtime.py (tar extraction) | medium | mitigate | Refuse archive members with absolute paths or `..` traversal segments before extracting, mirroring the existing win32 branch's `Path(entry.filename).name != entry.filename` guard |
| T-01-03 | Tampering | engine/runtime output directory | medium | mitigate | Reuse the existing symlink/junction refusal check (`RUNTIME.is_symlink() or resolve() != RUNTIME`) unchanged for the macOS branch |
</threat_model>
